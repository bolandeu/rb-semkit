## Problem

The library does everything, but only from Python. A person who works with a semantic core in files, and an agent that drives a shell, need one command that reads a table or a text, runs any chain of cleaning and analysis steps in the order written, and writes the result; and they need ready word lists (minus-words, stopwords, lists to combine, their own niche lists) by name, with the help showing which lists exist.

## Goal

semkit read core.xlsx drop-words @minus/universal remove-chars punctuation dupes --kind lemmas --action drop ngrams -n 2 write out.csv works; every library function is a step with its own --help; semkit lists shows every list (bundled, the Human's folders, the project) and a step that takes a list shows them in its help; an agent gets the same through --json, describe and --ai.

## Acceptance (Given–When–Then)

- Given a table file and a chain of steps, When semkit read IN step … step write OUT runs, Then the steps run in the order written over the current table and OUT holds the result; a step that makes a report (n-grams, metrics, clusters, coverage, comparison) makes its table the current one
- Given any public function of rb_semkit, When semkit describe --json runs, Then it is a step there with its arguments, and semkit <step> --help shows the help of the function in user terms; a function added to the library later becomes a step by one entry of the step table
- Given the find, remove and extract matchers, When used as steps, Then each pair is a named step (remove-words, extract-markers, find-regex, …), and keep-<matcher> / drop-<matcher> keep or drop the rows where the matcher finds something
- Given a change step, When it runs, Then it changes the working column in place; with --as NAME it writes a new column and keeps the old one
- Given IN or OUT '-', When the pipeline runs, Then it reads or writes JSONL on stdin or stdout, and nothing else goes to stdout; read --whole reads a text file as one cell; --column picks the working column, by default the first text column
- Given a pipeline, When it runs, Then after each step one line goes to stderr: the step, rows before and after, cells changed; with --trace FILE a row-level journal (row, step, before, after) is written; --quiet drops the stderr lines
- Given --dry-run, When the pipeline runs, Then it reads and runs every step and prints the summary, but writes no file
- Given OUT that exists, When the pipeline would write it, Then semkit refuses and names --overwrite; the file is written whole or not at all (a failed step or write leaves the old file as it was)
- Given a wrong step, argument or value, When the pipeline starts, Then semkit refuses before reading the input, naming the step, the argument and the allowed values (with --json: a JSON error with code, message, hint), and writes nothing
- Given a list argument, When it is @name, @path or a comma list in quotes, Then @name resolves in the project's .semkit/lists/, then the Human's folders (config lists = [paths], or SEMKIT_LISTS), then the bundled lists; @path reads that file; an unknown name is refused with the names that exist
- Given the bundled lists (the !SEMTools lists and the 66 Bukvarix lists: minus/*, stop/wordstat, combine/*), When semkit lists runs, Then it shows every list with its source, number of lines and description; semkit lists show NAME prints it; semkit lists add NAME FILE copies a file into the project or user folder (an existing name is refused without --replace), semkit lists rm NAME removes a list added there (never a bundled one)
- Given a step that takes a list, When its --help, describe or --ai is read, Then it shows the names of the lists that exist at that moment
- Given a new bundled list in a later version, When it is a text file in the list sources and one line in the list manifest (name, description, source), Then the build bundles it and the help shows it with no code change; a test fails when a file has no manifest line or a manifest line has no file
- Given 1M phrases in a parquet file, When a pipeline of 5 cleaning steps runs, Then it ends within the benchmark budget of the library steps plus read and write
- Given semkit --ai, When read by an agent, Then it explains the pipeline, the list syntax and gives typical pipelines (clean a core, the frequency dictionary of an article, a text against competitors, SERP clusters)

## Implementation decisions

- One chained-step group (Click chain) that starts with read and ends with write; the service commands (init, status, doctor, config, describe, skill, lists) stay as they are; ADR 0008.
- A step table: for each public function its step name(s), the working column, the kind (change, filter, report) and the arguments that need a CLI form (a list, a matcher); the steps are generated from the signatures and docstrings, the help from the docstrings.
- A pipeline state object: the current table, the working column, the step summaries; the read and write steps go through dataio (a required dependency of the CLI).
- A word-list library: a resolver (project folder, the Human's folders from the config and SEMKIT_LISTS, the bundled lists), a manifest of the bundled lists, the list commands; the library gets sk.word_list(name) so Python users resolve the same names.
- The Bukvarix lists come from the downloaded sources (UTF-8 with BOM, CRLF), are cleaned and bundled like the marker lists.

## Test seams

- The command line: semkit run in a subprocess or CliRunner, input files and stdin, output files, stdout, stderr and exit codes
- semkit describe --json: the contract of the steps and their arguments

## Out of scope

- Saved scenarios or recipe files: a pipeline is a shell line
- Downloading anything (pages, search results, frequencies, lists at run time)
- Clustering by embeddings
- A GUI or a web service
